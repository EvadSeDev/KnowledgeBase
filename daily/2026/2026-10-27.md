### Исходный вопрос

```text
Как отличить проблему Bean Validation от проблем десериализации, classloader и конфигурации в legacy JAX-RS приложении?
```

### Почему он был полезен

```text
Он заставил разделить цепочку на независимые этапы: Jackson → создание DTO → ручной Validator.validate → 
каскад @Valid → ConstraintValidator → обработка исключения. Это позволило не использовать queryTypes=["UNKNOWN"] 
как неверный тест QueryTypeValidator.
```

# Investigations

## Investigation #1

### Контекст

```text
В DEV отсутствовал ожидаемый лог QueryTypeValidator при наличии ручного вызова BeanValidationUtils.validate(request). Локальные тесты и DEV используют разные способы инициализации Jersey.
```

### Проблема

```text
Нужно было определить, вызывается ли QueryTypeValidator, проходит ли каскад через Filters и не используется ли в DEV устаревший class или Validator.
```

### Гипотезы

1. В runtime загружен старый Filters.class без @ValidQueryType.
2. Каскад не выполняется из-за null filters или запрос не доходит до BeanValidationUtils.validate.
3. Ошибка возникает на Jackson-десериализации либо в статической инициализации DebugService.
4. DEV использует другой classloader, WAR или версию Bean Validation.

### Выполненные проверки

- Найден единственный production-вызов BeanValidationUtils.validate(request).
- Найдено единственное создание Validator через Validation.buildDefaultValidatorFactory().
- Проверено наличие @Valid на ParameterJsonRequest.filters и @ValidQueryType на текущем Filters.java.
- Установлено, что BeanValidationUtils показывает только первое ConstraintViolation.
- Сопоставлены WebAppDescriptor и web.xml.
- Проверено, что UNKNOWN для enum не является тестом QueryTypeValidator.

### Вывод

```text
В текущем исходнике цепочка Bean Validation настроена корректно. Причина отсутствия QueryTypeValidator в текущем runtime не доказана; наиболее значимые варианты — stale deployment/classloader, отсутствие filters, десериализация до validate либо неполный диагностический вывод.
```

### Следующий шаг

```text
Недостаточно данных для подтверждения фактического Filters.class на DEV и полного набора ConstraintViolation.
```

# Lessons Learned

## Lesson #1

### Ситуация

```text
QueryTypeValidator не был виден в DEV, а состояние аннотации @ValidQueryType менялось между проверками исходника.
```

### Что произошло

```text
Текущий исходник содержит активную @ValidQueryType, поэтому одного чтения source недостаточно для вывода о runtime.
 Нужно сопоставлять source, target, WAR и classloader.
```

### Вывод

```text
Отсутствие лога или первого ConstraintViolation не доказывает, что валидатор не запускался. BeanValidationUtils 
получает полный Set, но показывает только первое нарушение.
```

### Как использовать в будущем

```text
Разделять Jackson-десериализацию, Validator.validate, каскад @Valid, ConstraintValidator и обработку исключения; 
проверять полный список нарушений и CodeSource классов.
```

# Knowledge Worth Saving

Знания, которые стоит сохранить в базе знаний.

- Bean Validation запускается вручную через BeanValidationUtils, а @Valid отвечает за каскад вложенного Filters.
- @ValidQueryType не зависит от Jersey package scanning: Hibernate Validator получает QueryTypeValidator через @Constraint(validatedBy=...).
- Jackson-ошибка enum возникает до Bean Validation.
- ExternalConfigurationListener только проверяет внешние ресурсы и требует точный file URL в ${catalina.base}/lib/lz.
- Рабочий legal-terms не подтверждает наличие SearchServiceEnv.properties.
- Отсутствие обязательного файла listener может сделать недоступным весь /service/*.
